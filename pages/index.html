GitLab × AI workflow

把项目交给 AI，不是把文件发给 AI。

GitLab 让 AI 读取同一份项目资料、保留每次修改记录，并把未经确认的改动隔离在独立分支中，经过检查后再合入正式版本。

Why GitLab

为什么让 AI
通过 GitLab 工作

GitLab 不只是放文件的地方。它给 AI 一套熟悉的入口，把资料、协作、自动执行和每次修改的来龙去脉放在一起，让 AI 更容易理解，也让人更容易检查。

01 · AI 熟悉的入口

不用为每个项目
重新教 AI

GitLab 自带命令行和接口，AI 已经理解这套通用用法：找到项目、读取资料、提交修改，都有现成的路径。

02 · 从资料到执行

把协作过程
自然串起来

知识库、页面、自动检查、机器人和执行环境可以接在一起，让 Agent 从“读懂”一路走到“完成并交付”。

03 · 唯一真理源

AI 最近的
可信入口

项目仓库保存当前版本、修改记录和讨论依据。大家看同一份内容，AI 也从这里开始，不再反复寻找“到底哪份是真的”。

Simple SOP

从新建项目，
到安全合入

第一次完成登录、令牌和业务项目配置。之后每个任务都遵循同一条路径：从正式版本开新分支，修改并检查，通过合并请求确认后再合入。

01
首次配置 · 先登录，再创建令牌

登录 GitLab，创建个人访问令牌

按下面 1-4 步操作。下方图示也要跟着点击切换 Tab 查看，不同 Tab 对应不同页面位置。

  1. 先登录。打开 GitLab 群组或项目页面；如果右上角显示 Sign in，先完成公司账号认证。
  2. 找到入口。登录后打开个人设置，进入“访问”，再点击“个人访问令牌”。
  3. 选择令牌类型。点击“生成令牌”，选择“旧版令牌”，填写名称和到期日。
  4. 设置并复制。按团队要求只勾选完成工作所需的权限，生成后立即复制令牌；离开页面后通常无法再次查看。

02
业务负责人操作 · 直接交给 AI

通过 AI 在 Design System Group 建立业务仓库

业务仓库统一创建在 L3-AI-Native / Design System。负责人准备业务名称、自己的 GitLab 账号和已沉淀项目目录，然后依次复制下方两段提示词给 AI。

  1. 填写业务名称。示例：小布笔记对应 xiaobubiji-design-system。
  2. 让 AI 创建空仓库。AI 必须先确认命名空间是 L3-AI-Native / Design System，不能创建到个人空间。
  3. 让 AI 上传项目。把 miniColorDesign 插件已经沉淀好的完整项目推送到新仓库。
  4. 负责人验收。打开仓库确认 main、README、Shared、业务目录和启动说明都已存在。
示例输入

业务名：小布笔记；仓库名：xiaobubiji-design-system。

最终结果

AI 返回业务仓库 URL、main 提交和本地启动方式。

仓库负责人：<负责人姓名或 GitLab 用户名>
GitLab 用户名：<用户名>
Personal Access Token：<个人访问令牌>

请按顺序完成：
1. 先确认目标命名空间确实是 L3-AI-Native / Design System。如果路径或权限不明确，停止并告诉我，不要改到个人空间。
2. 在这个 Group 下创建空白仓库 xiaobubiji-design-system，沿用 Group 的可见范围和默认权限。
3. 不要初始化示例代码，也不要把令牌写进 URL、日志、仓库或聊天摘要。
4. 创建后返回仓库网页地址、Clone with HTTPS 地址、默认分支状态和当前负责人。

现在只创建空仓库，不要上传项目。

提示词 2 · 上传已沉淀项目
请把 miniColorDesign 插件已经沉淀好的完整项目上传到刚创建的业务仓库。

已沉淀项目目录：<本地完整项目目录>
目标仓库 HTTPS：<刚创建仓库的 Clone with HTTPS 地址>
目标正式分支：main

请按顺序完成：
1. 读取项目内的 README、AGENTS.md、design-system.manifest.json 和 package.json，确认这是完整的 miniColorDesign 项目，不是只包含源码的临时目录。
2. 检查 git status 和现有 remote。保留原有 Git 历史；如果当前 origin 指向模板仓库，把它改名为 template，再把目标业务仓库设为 origin。
3. 检查是否误包含令牌、密码、个人信息、构建产物或不应公开的资料。发现风险先停止并告诉我。
4. 确认 Shared、业务 stories、业务 knowledge、assets 和启动脚本都在项目中。
5. 将当前确认版本提交到 main 并推送到目标仓库。不要 force push。
6. 推送后运行仓库要求的检查，并返回仓库地址、commit ID、检查结果和本地启动命令。

如果目标仓库不是 L3-AI-Native / Design System 下的仓库，停止操作。

04
交给 AI · 准备目录并启动服务

拉取 Shared + 业务项目，启动本地服务

把 Shared 公共仓库和业务仓库一起交给 AI。AI 先 clone 或拉取最新内容，再按两个目录各自的 README、package.json 和启动脚本启动服务。

本地目录

<工作区>/shared + <工作区>/<业务名称>，两个目录都要保留。

完成标志

两个仓库状态正常，Shared 与业务服务均已启动或明确报告阻塞。

直接复制给 AI · 准备本地工作区
请帮我准备一个 GitLab 工作区，包含 Shared 与业务项目。

GitLab 用户名：<用户名>
Personal Access Token：<刚创建的令牌>
Shared 项目 HTTPS：<Shared 项目 HTTPS 地址>
业务项目 HTTPS：<业务项目 HTTPS 地址>

请按顺序完成：
1. 检查 git 和 pnpm 是否可用；如果未安装或用户信息未配置，先告诉我。
2. 分别 clone 两个项目到以下目录，不要把令牌写入 URL、仓库、配置文件、日志或聊天摘要：
   - <工作区>/shared
   - <工作区>/<业务名称>
3. 如果目录已存在，先查看远端和分支，再拉取最新 main；不要覆盖未提交的修改。
4. 分别运行 git status、git remote -v、git branch --show-current，并读取两个目录的 README、AGENTS.md 和其他项目规则。
5. 在两个目录中查看 package.json 和项目文档，使用仓库已有的 dev / storybook / start 脚本启动服务；不要猜命令。
6. 最后告诉我：两个项目是否拉取成功、目录位置、当前分支、启动命令、服务地址和仍需我确认的事项。

现在不要修改、提交或推送任何内容。令牌只用于当前本地认证。
Shared 提供公共基础能力，业务目录承载本业务页面、知识和配置；启动失败时先报告原因，不要擅自改配置。
05
开始新任务 · 让 AI 创建分支

把具体任务交给 AI，从最新 main 开始

业务负责人只要写清任务目标和验收结果。AI 负责先同步 main，再建立本任务的独立分支，避免修改直接进入正式知识资产。

案例任务

为小布笔记补充“会议笔记分享面板”的组件、使用说明和 Story。

案例分支

feat/meeting-note-share-panel

案例提示词 · 创建任务分支
请在小布笔记 Design System 仓库中为下面的任务创建独立分支。

任务目标：补充“会议笔记分享面板”的组件、使用说明和 Storybook 示例。
验收结果：
- Storybook 中可以查看分享面板的默认态和已选择态
- 使用说明写清什么时候使用、什么时候不使用
- 不修改 Shared 公共组件，除非先说明原因并获得确认

请按顺序完成：
1. 读取仓库的 README、AGENTS.md、design-system.manifest.json 和业务知识入口。
2. 检查当前工作区是否有未提交修改。如果有，先告诉我，不要覆盖。
3. 切换到 main，拉取远端最新版本。
4. 从最新 main 创建分支 feat/meeting-note-share-panel。
5. 返回当前分支名、main 的最新 commit ID，以及准备修改的目录。

现在只准备分支和任务上下文，不要提交、推送或创建合并请求。
每次复制时替换任务目标、验收结果和分支名。一个任务只使用一个分支。
06
修改完成后 · 提交并推送任务分支

确认修改后，提交、推送，再发起合入

修改完成并确认结果后，让 AI 按固定顺序提交和推送当前任务分支。不要直接推送 main，也不要跳过合并请求。

提交前

先看 git diff 和检查结果，只保留本任务的修改。

提交后

返回分支名、commit ID、远端地址和创建合并请求的入口。

直接复制给 AI · 提交并推送
请完成下面的任务：

任务目标：<要新增或修改什么>
我已经确认修改结果，请按下面顺序完成：
1. 再看一次 git diff 和项目要求的检查结果，确认只包含这个任务。
2. 在当前任务分支提交修改，提交信息要能说明这次变化。
3. 推送当前任务分支到远端，不要推送 main。
4. 返回分支名、commit ID、推送结果和创建合并请求的入口。

不要直接合入 main，也不要删除任务分支。
业务负责人确认后再执行；提交和推送只针对当前任务分支。
07
正式知识资产 · 维护 main，再合入

让业务负责人维护正式知识资产并合入 main

业务仓库的正式知识资产只认 main：README、页面、knowledge 和入口都要有人持续维护。任务分支只承载待确认修改，审核通过后才通过合并请求进入 main。

  1. 创建合并请求。选择当前任务分支 → main，写清这次修改的目的和范围。
  2. 业务负责人审核。检查内容、页面、知识和启动结果，确认正式资产仍然可用。
  3. 解决意见再合入。自动检查通过、审核意见关闭后，才能点击 Merge 合入 main。
  4. 合入后维护。确认 main 已更新，必要时刷新 Pages，并删除已合入的任务分支。
正式资产

只认 main 中已确认的 README、pages/、knowledge/ 和运行入口。

完成标志

MR 已合入、main 可用、负责人知道如何继续维护，任务分支记录仍可查询。

01

分支 → main

合并请求的目标始终是 main，不把待确认内容直接写进正式版本。

02

负责人维护

业务负责人负责正式知识资产的正确性、完整性和持续更新。

03

检查通过

自动检查、页面预览和启动结果都留在合并请求记录里。

04

合入后可追溯

main 更新、Pages 发布和任务分支删除都能回到同一条记录。
